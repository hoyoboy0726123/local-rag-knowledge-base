# 本機知識庫（React + FastAPI）

把研發流程文件放進來，用自然語言問，**回答只依據知識庫內容、每句都能追溯到來源**。
AI 運算全部在本機完成，文件不會離開這台電腦。

## 怎麼跑起來

**雙擊 `start.bat`。**

首次執行會建立虛擬環境、安裝套件、**建立資料庫與展示帳號**，然後啟動；
**之後每次都直接啟動**，不再重跑安裝。瀏覽器會自動開啟 <http://localhost:8600>。

| 展示帳號 | 角色 | 密碼 |
|---|---|---|
| `admin` | 知識庫管理員 | `demo1234` |
| `user01` / `user02` | 一般使用者 | `demo1234` |

> **要掛到區網給別人連之前，先把這三組密碼改掉。**
> 它們就寫在這份公開的 README 裡，等於門是開的。啟動時主控台會警告還有誰
> 沒改。改的地方：登入後「個人設定 → 修改密碼」，或用 admin 到「帳號管理」
> 重設。
>
> JWT 簽章金鑰**不需要你處理**——首次啟動會自動產生一組隨機金鑰存進資料庫，
> 每台機器都不同。需要多台機器共用時，設環境變數 `KB_JWT_SECRET` 覆寫即可。

**知識庫預設是空的。** 這套系統與領域無關——登入後到「知識庫維護」指定你自己的
文件資料夾，按「增量更新」建立索引即可。附一批範例文件反而會讓人以為
它只能用在那個場景。

想先看效果的話，可以產生一組 NUC 研發流程的示範文件（12 份 Markdown）：

```bash
venv\Scripts\python.exe seed_data.py --with-demo-docs
```

> `knowledge.db` **不在版控中**——它存著每份文件解析後的完整全文，
> 推上公開儲存庫等於發佈文件內容。`start.bat` 首次執行會自動建好。

### 事前需要什麼

| 項目 | 必要性 | 說明 |
|---|---|---|
| **Python 3.11 或 3.13** | **必要** | <https://www.python.org/downloads/>，安裝時勾「Add python.exe to PATH」 |
| **Ollama** | AI 問答需要 | <https://ollama.com/download>。沒有它也能啟動，瀏覽與管理功能正常，只是不能問答 |
| Node.js | **不需要** | 前端已預先建置好。只有你要**改**前端才需要 |

Ollama 裝好後拉三個模型：

```bash
ollama pull bge-m3                   # 向量（多語系，1.2 GB）
ollama pull gemma4:12b               # 生成回答（7.6 GB）
ollama pull qwen3-vl:8b-instruct     # 視覺解析，只有要讀圖片／掃描件才需要（6 GB）
```

### 為什麼是這三個（都是實測選出來的）

| 角色 | 模型 | 選它的理由 |
|---|---|---|
| **向量** | `bge-m3` | **多語系**且 context 8192。原本用 `bge-large-zh-v1.5`（中文專用、context 512），實測**中文問句撈不到英文文件**——同一批問題命中數 12/36 → **22/36**。8192 的 context 也解除了「切片超過 500 字會被無聲截斷」的限制 |
| **生成** | `gemma4:12b` | 支援工具調用（Agent 模式必要）。`gemma4:e4b` 也可用、快約 32%，但磁碟大 2 GB |
| **視覺** | `qwen3-vl:8b-instruct` | 拿 17 個欄位的驗收表實測 **17/17 全對**。詳見〈不是每個宣告 vision 的模型都真的在看圖〉 |

**不能用的模型**（都實測過）：

| 模型 | 問題 |
|---|---|
| `gemma4:e2b` | 追問時**回傳空白答案**，10 次全空。測試套件卻是全過的——那項只跑一次剛好矇對 |
| `qwen3:8b` | 有對話脈絡時**會編造知識庫沒有的內容並附上假的來源編號**——問「請假流程」（知識庫完全沒有）連續三次編出完整的五步驟制度。同一題**沒有對話脈絡時則正確拒答**，所以只測單題會誤判它可用。加上防幻覺把關後可用（見下），但仍偶爾答成上一輪的問題 |
| `gemma4:e4b` 當 VLM | `ollama show` 有列 `vision`，但實測 17 項全錯——送純色圖也照樣產出「流程圖」描述。**它根本沒在看圖** |

> **向量與生成模型不能混用。** 把向量模型設成生成模型的話，每次檢索都會失敗（HTTP 501）——
> 這個坑實際踩過。「模型與設定」頁會分開列出兩者。

> 換過 embedding 模型後**必須執行全量重建**——不同模型的向量空間不相容。

改埠：編輯 `start.bat` 裡的 `set "APP_PORT=8600"`。

## 文件輸入

### 兩種放檔案的方式，效果完全相同

**A. 介面上傳**：知識庫維護 → 文件與索引 → 上傳文件
**B. 檔案總管**：直接把檔案複製到 `sample_knowledge_base/` 底下

索引是**掃描資料夾**，不是只認上傳來的檔案。所以要一次放進幾十份文件，
用檔案總管拖進去反而快。

### 檔案存到哪裡

```
知識庫根目錄/
├── 管理辦法總則.md        ← 直接放根目錄 = 「通用」知識庫
├── 跨部門窗口一覽.md
├── 測試規範/              ← 每個子資料夾就是一個知識庫，名稱自訂
│   ├── NB Test Plan.pdf
│   └── MIL-STD-810H.xlsx
└── 教育訓練/
    └── 基礎課程.pdf
```

**一個知識庫 = 根目錄下的一個子資料夾；直接放在根目錄的檔案屬於「通用」。**
資料夾是唯一的真相來源：用檔案總管建資料夾、丟檔案、搬檔案，跟在介面上操作是
同一件事，全量重建不會丟失分類。

上傳時可以選既有知識庫、**當場新建一個**、或放通用；之後在「知識庫」頁可以把文件
搬到別的知識庫——搬移只搬檔案並同步路徑，**不需要重新向量化**。空的知識庫才能刪，
裡面還有文件會被拒絕，要先搬走。

**同名檔案不會被覆蓋**，會自動加序號（`報告.md` → `報告_2.md`）。

### 支援的格式

| 類別 | 副檔名 | 怎麼處理 |
|---|---|---|
| **文件** | `.pdf` `.docx` `.doc` `.pptx` `.ppt` `.xlsx` `.xls` `.msg` `.eml` `.txt` `.md` `.csv` `.json` `.xml` `.html` `.htm` | MarkItDown 統一轉成 Markdown |
| **圖片** | `.png` `.jpg` `.jpeg` `.bmp` `.gif` `.webp` `.tiff` | 交給視覺模型描述內容 |

其他副檔名**會被擋下並在上傳結果列出原因**，不會靜默略過。空檔案也會被擋下。

### 強制視覺解析（圖多的文件要勾）

**預設只讀文字層。** 簡報裡的架構圖、流程圖、表格截圖**不會進入索引**——
那往往才是重點。

勾了「強制視覺解析」之後：

* **文字與圖片兩者都保留**，不是二選一
* 圖片內容附在文字層後面，以 `## 圖片內容（由視覺模型判讀）` 區隔
* 來源卡片上看得出哪一段是模型判讀的

實測一份 32 張圖的簡報：不勾 12,574 字 → 勾了 17,745 字，**多出 5,171 字的圖表內容**。

兩個地方可以勾：

| 位置 | 時機 |
|---|---|
| 上傳區的核取方塊 | 上傳當下 |
| 文件清單每一列的「視覺解析」 | 已經上傳過的檔案 |

> **勾了不會立刻生效**，要按一次「增量更新」。介面會提示這件事。
> 系統知道你改了這個開關，所以即使檔案內容沒變也會重新解析那一份。

需要視覺模型：`ollama pull qwen3-vl:8b-instruct`

**兩個上限要知道**：

* 單一檔案最多解析 **10 張圖／10 頁**，超過的部分會在內容裡明確標注
* Office 檔內**小於 20 KB 的圖片會跳過**——那多半是圖示、項目符號、公司 logo，
  描述它們只會得到「一個藍色小圖示」這種對檢索毫無幫助的內容

掃描型 PDF（整頁是圖片、選不到文字）會**自動**走視覺路徑，不用特別勾。

### 文件清單

「知識庫文件」面板列出**磁碟上所有檔案**，不是只列已索引的——
剛上傳、還沒建索引的檔案會標成琥珀色的「尚未索引」，你才能確認檔案真的存進去了。

每一列可以：**勾視覺解析**、**刪除**。

## 索引與向量管理

### 索引在做什麼

```
掃描資料夾 → 解析成 Markdown → 切片 → 算向量 → 存進 sqlite-vec
```

| 步驟 | 細節 |
|---|---|
| **解析** | MarkItDown 統一處理所有格式；圖片或掃描件走視覺模型 |
| **正規化** | 還原 MarkItDown 為了塞進表格而做的轉義；長文欄位的表格改寫成逐筆記錄 |
| **切片** | 在**最強的可用邊界**切，每片上限 500 字，續段會補上出處 |
| **算向量** | 每片送 embedding 模型，一次 16 片批次處理 |
| **儲存** | 向量存進 `vec_chunks`（sqlite-vec 虛擬表），與切片以 `chunk_id` 對應 |

### 為什麼上限是 500 字

**這個數字原本是 embedding 模型的硬限制。** 舊的 `bge-large-zh-v1.5`
`context_length` 只有 512 tokens（中文約 1 字 1 token）。實測固定前綴、只改結尾：

| 前綴長度 | 換掉結尾後向量的變化 |
|---|---|
| 480 字 | cos = 0.994 |
| 500 字 | cos = 0.999 |
| **520 字** | **cos = 1.000000 ← 結尾完全沒被讀進去** |

超過的部分不是「權重較低」，是**根本沒進入向量**，永遠不可能被語意檢索找到。

**改用 `bge-m3` 之後這條硬限制已經解除**（context 8192，是原本的 16 倍），
但 `chunk_size` 仍維持 500——切片變大不見得更好：一個向量代表三千字會不夠聚焦，
反而稀釋檢索精準度。想調大可以到「模型與設定」改，改完需要**全量重建**。

### 切片切在哪裡

邊界是一道階梯，找得到就用，找不到才往下退：

```
1. 結構標記   ## 標題 ／ <!-- Slide N --> ／ 第 N 頁
2. 空行段落
3. 句尾       。！？；
4. 硬切       最後手段
```

**相鄰單元塞得下會併回去。** 一份 374 字的規範有 6 個 `##`，若每個都切開會變成
6 個 60 字的碎片，每片都短到沒有脈絡——結構標記的用途是「提供可切的地方」，
不是「非切不可」。

**一個單元被迫拆成多段時，第 2 段以後會補上 `> 出處`**（章節名／投影片編號／
頁碼／該筆記錄的標題）。沒被拆的段落本身就從標題開頭，不需要重複。

> 這是為了修一個實際發生的問題：一份問答紀錄 Excel，每列的「完整答案」欄有
> 數千字。MarkItDown 轉出來的 Markdown 表格**一列就是一行、整份沒有任何空行**，
> 舊切片器只認空行，只能硬切——127 個切片裡只有 1 個帶得到欄位表頭，
> 63% 看不出自己在回答什麼問題。修正後 180 個切片**全部**帶得到自己的題目。

### 表格的兩種處理

| 表格型態 | 處理方式 |
|---|---|
| 欄位都短（人員一覽、里程碑表） | **維持表格原樣**，渲染出來就是表格 |
| 有欄位塞了長文（>200 字） | 改寫成逐筆記錄：短欄位進 `###` 標題，長欄位獨立成段 |

Markdown 表格的一列必須在同一行，所以 MarkItDown 會把儲存格內的換行寫成字面
`\n`、把 `**粗體**` 轉義成 `\*\*`。用 openpyxl 讀原始檔驗證過儲存格裡本來就是
真換行與真的 `**`，所以這個還原是可逆的，沒有資訊損失。

重疊 80 字是為了讓跨段落的語意不會被切斷——一句話橫跨兩片時，兩片都有它。

### 增量更新 vs 全量重建

| | 增量更新 | 全量重建 |
|---|---|---|
| 未變更的檔案 | **跳過**（比對 SHA-256） | 全部重新解析 |
| 已刪除的檔案 | 清掉它的索引 | 同左 |
| 改過「視覺解析」開關的檔案 | **會重新解析**（不只看檔案內容） | 同左 |
| 你手動刪掉的切片 | **不會回來** | **會原樣長回來** |
| 你補的檢索關鍵字 | 保留 | **保留** |
| 你編輯過的切片內容 | 保留 | **保留** |
| 換了 embedding 模型 | 擋下並要求改用全量重建 | 正確重建 |

**日常用增量更新就好。** 全量重建只在換 embedding 模型、或懷疑索引壞掉時才需要。

> **換 embedding 模型必須全量重建。** 不同模型的向量維度可能不同，
> 而向量表的維度在建立時就固定了。系統會先探測維度，不符時擋下增量更新
> 並告訴你要改用全量重建——沒有這道檢查的話會寫入全數失敗、留下一個空知識庫。

### 進度顯示

索引過程**逐則即時顯示**，包括視覺解析的每一張圖：

```
找到 13 個可解析的檔案
[13/13] 產品簡報.pptx
  產品簡報.pptx：強制視覺解析中，這一份會比較久…
    找到 32 張可解析的圖片
      視覺解析 圖片 1/10（image1.jpeg）…
      視覺解析 圖片 2/10（image10.jpg）…
```

視覺解析每張圖約 3–11 秒，所以一份圖多的簡報要跑 1 分鐘以上——
有進度顯示才不會以為當機了。

### 刪除文件會清掉什麼

刪一份文件不是只刪一列，而是**五個地方一起清**：

| # | 對象 | 不清會怎樣 |
|---|---|---|
| 1 | 切片 | 檢索仍會撈到已刪的文件 |
| 2 | **向量** | sqlite-vec 虛擬表不會因為切片被刪就跟著消失，會留下孤兒向量 |
| 3 | 檢索關鍵字備份 | 日後上傳**同檔名**的新檔案時，舊關鍵字會被套到新內容上 |
| 4 | 解析錯誤紀錄 | 「解析狀態」頁一直顯示一個已不存在的檔案 |
| 5 | **磁碟上的檔案** | 下次建索引又會被掃回來 |

刪除會跳確認框，並標明會連帶刪掉幾個切片。**這個動作無法復原。**

### 檢索測試

輸入一個問題，看實際會撈到哪些切片與**距離**（越小越相似）。
這是判斷索引品質最直接的工具——AI 答不出來時，先來這裡看它到底找到了什麼。

> 系統**不靠距離門檻判斷相關性**，相關性交給 LLM 判斷。
> 那個 1.35 的門檻只是保險絲，擋掉極端無關的情況。

## 切片工作台

「知識庫維護 → 切片內容」。左欄**依文件分組、可展開**——一封 `.msg` 郵件可能切出上百段，
平鋪成一長串完全沒辦法找東西。搜尋時會自動全部展開。

每個切片可以做三件事：

### 1. 補檢索關鍵字

使用者的口語常跟文件用語對不上——「以前踩過什麼雷」對「Lesson Learnt」。
在這裡補同義詞，可提高這一段被找到的機率。

* **只影響向量比對**，不會出現在回答或來源卡片裡
* 存檔後**立刻重算這一段的向量**，檢索結果馬上改變
* 重新索引時自動還原，不會消失

### 2. 編輯內容

用來清掉解析出來的噪音——郵件的收件人清單、簽名檔、免責聲明、重複的頁首。
這些文字會佔用檢索名額卻答不出任何東西。

編輯有三道保障：

| 保障 | 作用 |
|---|---|
| **存檔立刻重算向量** | 否則改了內容檢索完全不變，你以為調好了其實沒有 |
| **保留原文** | 隨時可展開比對「檔案原本解析出什麼」，可一鍵還原 |
| **另存一份** | 重新索引（含全量重建）後自動套回，不會消失 |

編輯過的切片會標「✎ 已編輯」，並顯示原文幾字 → 現在幾字。

> 可追溯性沒有被犧牲——保證從「內容必定等於原文」換成「**內容的來歷必定查得到**」，
> 後者才是真正需要的。

### 3. 刪除切片

讓這一段立刻退出檢索範圍。

> **這個刪除不是永久的。** 切片是從檔案解析出來的衍生資料：
> 「增量更新」不會讓它回來（檔案沒變就跳過），但**「全量重建」會原樣長回來**。
> 要永久排除，得改動來源檔案本身，或改用「編輯內容」把那段文字刪掉
> （編輯是會被保留的）。

## AI 問答

**三欄：對話清單 ｜ 對話串 ｜ 參考來源**

* **回答逐字出現**，不是等整段跑完才跳出來
* 回答上方先顯示**檢索膠囊**（`◐ 檢索 DVT 散熱驗證 · 6 段`），讓你知道 AI 做了什麼
* 引註 `[1]` 是可點的色塊——點了會**選取＋展開＋捲動**到右側對應的來源卡
* 來源卡可展開看全文，或開浮層以 Markdown 渲染閱讀（含表格）
* **追問聽得懂前文**：問完之後直接說「還有嗎」「那 X 呢」
* 回答下方有 **📄 顯示原始片段**：點開就是檢索到的原文，未經 AI 改寫

**檢索範圍**可勾選一個或多個知識庫（含通用），預設全部。限定範圍是硬過濾：範圍外的文件連候選都不會進。

### 為什麼要「顯示原始片段」

AI 的敘述再怎麼寫都是改寫，而規格表、對照表這類內容**原文的形式本身就是最好的
答案形式**。實測一張「大類／敘述」對照表被改寫成條列後，代號欄整欄消失——而
代號與名稱的對應正是那張表存在的意義。

提示詞可以要求模型保留表格，但那仍然靠模型配合；這個按鈕是**確定看得到原文**
的入口。預設收合，需要的人點一下就好。

### 查不到就說查不到

**問知識庫沒有的主題時，系統會回「知識庫中查無足夠資訊。」而不是猜。**

這件事不是靠提示詞交代，而是程式流程的一部分，分三層：

1. 檢索完先判斷「這批資料有沒有回答到問題」，沒有就不把內容交給模型
2. 作答後再判斷「答案是不是從這批資料寫出來的」
3. 全程沒撈到相關內容時，**不管模型寫了什麼都不採用**

第三層是硬保證。系統指示裡早就有「查不到就說查無資訊」這條規則，但它要跟另外
二十幾條競爭注意力，實測會被忽略——`qwen3:8b` 在有對話脈絡時連續三次編出完整
的請假流程並附上假的來源編號 `[7]`。

距離門檻救不了這件事：那題最近的切片距離 1.048，比會誤擋 43% 合理問題的門檻
還低。距離量的是「語意像不像」，而這裡要判斷的是「有沒有回答到」，是兩件事。

### 從來源直接開啟原始文件

來源卡展開後有兩個入口，浮層上方還有一排動作：

| 動作 | 做什麼 | 會不會存檔到你電腦 |
|---|---|---|
| **看這段全文** | 顯示 AI 實際讀到的那一段切片 | 否 |
| **開啟完整文件** | 直接顯示**整份**文件解析後的內容（表格會正確渲染） | **否** |
| **在新分頁開啟** | 用瀏覽器內建檢視器開原始檔 | 否 |
| **下載原始檔** | 取得原汁原味的檔案 | 是 |
| **用本機程式開啟** | 用 PowerPoint／Excel 等預設程式開啟 | 否（直接開原檔） |

**「開啟完整文件」是主要路徑**——不必下載就能讀完整份文件，而且看到的
跟 AI 讀到的完全一致。要原始排版、字體、圖片位置才需要下載。

**「在新分頁開啟」只對 PDF 與圖片出現。** 白名單是 `.pdf` 與 5 種點陣圖，
其餘一律退回下載，而且**後端也會擋**（手打網址繞不過去）。三種排除理由不同：

| 排除的格式 | 為什麼 |
|---|---|
| Office 檔（pptx/xlsx/docx） | 瀏覽器無法原生渲染，給了也只會變下載，讓人以為壞掉 |
| `.md`、`.txt` | blob URL 下瀏覽器常忽略 charset，改用系統預設編碼，**中文會整片變亂碼**（實測踩過）。這類檔案走「開啟完整文件」才對 |
| `.svg`、`.html` | **安全問題**。blob URL 會繼承本頁來源，這兩種格式裡的 `<script>` 會在本應用的 origin 下執行，讀得到 sessionStorage 裡的 JWT——上傳一個檔案就能竊取其他人的登入狀態 |

**「用本機程式開啟」只在你自己的電腦上跑這套系統時才出現。**
`os.startfile()` 是在**執行後端的那台機器**上開檔；系統若架在區網伺服器上，
遠端使用者按下去只會讓檔案開在伺服器的螢幕上。所以後端會檢查請求是否來自
localhost，不是就回 403，前端也不會渲染這顆按鈕——寧可沒有，也不要放一顆
點了沒反應的按鈕。

> 瀏覽器**不允許**網頁靜默把檔案寫進你的暫存區再叫起本機程式執行——
> 那是惡意網站落檔執行的經典手法，屬於沙箱紅線。所以區網使用者要用
> PowerPoint 開，必然得先下載。下載完在瀏覽器的下載清單點一下即可開啟，
> 部分瀏覽器還能設定「這類檔案總是自動開啟」。

**這些路徑只讀得到知識庫裡真正被索引過的文件。** 檔案路徑是前端傳來的
查詢參數，後端一律比對 `documents` 表白名單後才放行，不在索引裡的一律 404。

**對話紀錄在左欄**，點任一則就能載入並接著問。
**只有自己看得到，管理員也看不到**——那是私人的工作紀錄。

> 知識庫沒有的內容，系統會直接說查無資訊，**不會臆測**。
> 這是程式層強制的：沒有檢索過就不會有回答送出。

## 其他頁面

**知識庫**（所有人；管理員可管理）
列出每個知識庫與文件數，點進去看該庫的文件，可線上閱讀（Markdown 正確渲染，
表格是表格）與下載。「通用」永遠在第一個。管理員在這一頁可以新建、改名、刪除
（空的才行）知識庫，並把文件搬到別的知識庫。

**模型與設定**（管理員）
切換生成／向量／視覺模型，以及**上下文視窗下限**（`num_ctx`）。

上下文視窗是「模型單次能讀進去的最大量」，預設下限 8192。**設太小時超出的
檢索內容會被安靜丟掉**，模型收到殘缺的提示，症狀是答非所問或把系統指示複述
一遍——不會有任何錯誤訊息。這是下限，檢索結果較多時系統會自動往上調
（8K → 16K → 32K）；調高會增加顯示記憶體佔用，可能使模型被拆到 CPU 而變慢。

### 重排序模型（選配，預設不附帶）

同一頁下方有「重排序模型」區塊，可**一鍵下載（571 MB）並立即生效，不必重啟**。

**什麼時候需要它**：向量檢索是雙塔架構，問題與切片各自編碼再比距離，
分不出「沾邊」與「切題」。文件一大就撐不住——實測一份 400K 字的測試計畫，
30 段候選的距離全部擠在 **0.922–0.962**（只差 0.04），等於沒有排序能力。
Cross-encoder 把「問題 + 切片」一起讀，才能真正分出相關性。

實測同一批問題，開關重排序的差別：

| 問題 | 來源 | 關閉 | 開啟 |
|---|---|---|---|
| DVT 有哪些必要產出物 | 小型 Markdown | 5/5 | 5/5 |
| 量產移交檢查表有哪些分類 | 小型 Markdown | 5/5 | 5/5 |
| 原物料類別代號有哪些 | PDF + VLM（14K 字） | 6/7 | **7/7** |
| 有哪些壓力測試 | PDF（400K 字） | 5/6 | **6/6** |

**結論：小文件用不到，大文件需要。** 等你上傳自己的規格書、發現列舉不完整時
再下載即可。

**知識庫太小時系統會自動跳過重排序**，不必手動關。重排序的價值來自「從一大堆
候選裡撈出埋在後面的那一段」；候選池已經涵蓋知識庫一大半時，它做的不是篩選而
是把整個知識庫重排一遍。實測一個 25 個切片的知識庫：成本穩定 6.0 秒（佔一題總
耗時的四分之一）、確實改變了檢索結果，**但答案品質沒有差異**（開與關都 6/6）。
知識庫長大後它會自動回來工作。

技術細節：用 ONNX Runtime 跑 `bge-reranker-v2-m3`（量化版）。
`onnxruntime` 本來就在相依裡（MarkItDown 帶進來的），只多一個
`tokenizers`（3 MB）——**完全不需要 PyTorch**，維持本專案「不引入 torch 依賴鏈」的原則。
模型不存在時整條路徑自動跳過，功能照常運作。每次查詢約多 2 秒（CPU）。

## 疑難排解

| 症狀 | 原因與處理 |
|---|---|
| 問答說「查無足夠資訊」但文件明明有 | 到「檢索測試」輸入同一個問題看撈到什麼。撈不到 → 去切片內容補檢索關鍵字 |
| 切片內容跟原始文件對不上 | 是**解析階段**掉的，不是檢索問題。圖表內容要勾「強制視覺解析」 |
| 上傳沒反應 | 上傳區會顯示結果或錯誤原因。若完全沒訊息，看瀏覽器主控台 |
| 索引卡住不動 | 開了視覺解析的檔案本來就慢（每張圖 3–11 秒），進度會逐則顯示 |
| 側邊欄顯示「引擎未就緒」 | Ollama 沒啟動，或模型沒裝。瀏覽與管理功能不受影響 |
| 換了 embedding 模型後檢索全失敗 | 必須執行**全量重建**。系統會擋下增量更新並提示 |
| 改了程式碼但畫面沒變 | 前端要重新建置（`cd frontend && npm run build`），後端要重啟 |
| 卡在 `Installing dependencies` 很久 | 正常現象，首次要安裝約 500 MB 的套件，視網路約 3–8 分鐘。**不要關視窗** |
| 安裝失敗、pip 連線逾時 | 公司網路多半需要 proxy。先執行 `set HTTPS_PROXY=http://你的proxy:port` 再跑 `start.bat` |
| 顯示埠 8600 已被占用 | 上一次的程式還在背景。用工作管理員結束 `python.exe`，或修改 `start.bat` 裡的 `APP_PORT` |
| 想把資料重置成初始狀態 | 關掉程式 → 刪除 `knowledge.db` → 執行 `venv\Scripts\python.exe seed_data.py`（重建帳號與 12 份範例文件）→ 啟動後以 `admin` 登入，到「知識庫維護」按**增量更新**重建索引 |
| 想整個重裝環境 | 刪除 `venv` 資料夾，再跑一次 `start.bat` 即可重新安裝 |

**資料都在哪**

| | 位置 |
|---|---|
| 原始檔案 | `sample_knowledge_base/` |
| 索引、切片、向量、帳號、對話 | `knowledge.db` |

整包複製這個資料夾給別人，對方拿到的是**完整可用**的知識庫。
